# WOH.13 — Demonstrating prevention, not a malfunctioning home

Version: 0.2.0. Status: accepted demonstration target. No physical demonstration has been qualified by writing this document.

## Product claim

The demonstration shows that a prohibited draft cannot affect the active home. It must not install conflicting automation on a real light and then rely on a detector to stop the loop. The bad draft is data submitted to a credential-free admission process.

## Complete demonstration profile

**H13-01.** Preinstall a qualified local DistilBERT intent checkpoint/tokenizer, the exact Maude executable/model closure, the app and profiles. WAN is disconnected. DistilBERT is required in this complete presentation profile because it demonstrates untrusted interpretation; a separate typed-input run proves Home works without it.

The classifier maps an ordinary phrase to a bounded candidate with visible uncertainty. The planner resolves current authorized targets and constraints. No classifier score implies safety or device identity.

**H13-02.** Submit a versioned fixture of individually plausible but conflicting draft rules. Show the actual finding: a static conflict, reachable bad state or qualified cycle witness, whichever the checker really established. Do not call pairwise cascade detection an infinite-loop proof. Do not render an invented transition trace from a terminal-state-only result.

```text
draft -> structural/model checks -> real finding -> rejected
active revision unchanged; mutating device calls = 0
```

Prove the zero-call assertion at the dispatcher/driver boundary, not only on the screen. Keep production credentials inaccessible to fixture replay. A timeout or unsupported model shows inconclusive/rejected, never green.

## Positive path

**H13-03.** Use a corrected admitted rule profile or direct authorized Light request and show its declared admission basis. If Maude has not established a positive temporal property, do not label the action 'formally proved safe'. The restricted structural profile and deterministic runtime guards can provide a separate honest admission basis. Execute the qualified real light command, then display the receipt and independently read reported state.

The demonstration must distinguish classification, admission, protocol acknowledgement and observed state. Show at least one ambiguous phrase requiring clarification and one verifier-unavailable case that leaves existing valid control available.

## Safety and venue resilience

**H13-04.** Use a synthetic smoke fact only inside an isolated lab scope. It cannot be confused with a real detector report or change production alarm handling. A physical manufacturer self-test, if selected, is separately labelled and does not test every safety property. No smoke generation, remote hush, flashing real alarms or live conflicting rule installation is required.

Use a private local AP/network and consented devices, not uncontrolled conference Wi-Fi. A deterministic software peer is a labelled fallback when RF is unavailable. It can prove admission behavior but cannot claim live bulb or detector evidence. The native UI may fail without corrupting the active rule revision; the CLI can inspect the same receipts.

## Acceptance

H13-T1: actual classifier and checker run locally with identified artifacts. H13-T2: bad draft leaves active digest and physical outputs unchanged. H13-T3: every displayed witness is attributable to executed checker output. H13-T4: positive actuation displays its real admission basis. H13-T5: ambiguity, timeout and RF loss have honest outcomes. H13-T6: simulation has no production mutation credentials.
