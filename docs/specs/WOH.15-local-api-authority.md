# WOH.15 — Headless API and controller authority

Version: 0.1.68. Status: accepted target. Named operations below are contract names unless an implemented subset is identified below.

## One semantic service

`record_rule_review` accepts exactly `api_version`, `operation`, `credential`, `rules`, `authority_epoch`, `operation_id` and `expected_revision`. It uses the same bounded review gate and ten-second deadline as preview, but is a durable mutation: a timed-out response is `outcome_unknown`, and the caller resolves it with `rule_review_status` under the original epoch and operation ID. Status accepts exactly `api_version`, `operation`, `credential`, `authority_epoch` and `operation_id`. Both require current `rule:review` permission; status is principal-private and returns only the original scalar summary and digests. Recorded review does not grant control permission or create an activation endpoint. `record-rule-review EPOCH OPERATION_ID EXPECTED_REVISION RULES_FILE` and `rule-review-status EPOCH OPERATION_ID` expose the same contracts through the CLI.

**H15-01.** Provide versioned operations for discovery sessions, candidate inspection, enrollment, capabilities, snapshots/history, command submission/status, draft validation/qualification/activation, automation suspension and maintenance. The Elixir API, CLI, native shell and network facade consume this boundary. No client opens the database or writes vendor packets directly.

The authenticated enrollment boundary is now exposed as strict `lifx_enroll` and `lifx_rereview` local operations. A distinct `enroll:review` credential is checked before capture access and again against the reviewed operator inside the Store transaction; granting `control:ordinary` does not grant enrollment review. The request contains only session, candidate, packaged-profile, Home-Thing and review references. The authority derives candidate/interview evidence from the one-use host capture and derives the complete declaration and qualification reference from compiled profile data. Caller-authored evidence, stable IDs, capabilities and profile bodies make the closed request shape fail.
An exact in-process retry of the current original enrollment returns its original revision across restart without a second authority event. Socket capture consumption instead makes a lost reply recover through `enrollment_status` under the original review reference; the client never recreates evidence. A changed Thing or review reference conflicts, and a superseded original review cannot masquerade as the current binding. A fresh current re-review by the same operator retains history and returns its binding decision revision. Its transaction may append invalidation events after that decision revision, so callers seeking the final Store watermark use a fresh read.

The same enrollment permission gates a fresh re-review of an existing binding. The original operator and reviewed identity must match, and a new review reference is retained in history. Other principals cannot revise that identity merely because they control the Thing.

The Store also has an authenticated in-process direct Light-power promotion boundary. It cannot be reached through the local socket. A separately authorized in-process `qualify_lifx_power` operation can now create its required profile record only from a current enrolled basis, nine signed cases and a distinct signed physical-review decision against host-pinned public keys. Neither qualification nor promotion is a socket route. An opt-in supervised worker now claims qualified queued power work, records the pre-send handoff fence, sends through the pinned LIFX transport and settles the durable ledger from bounded readback. The default host has no reviewer keys, the worker is disabled unless explicitly configured, and ordinary socket mutation therefore still returns `held` in the default installation.

The existing authenticated cancel operation now withdraws either held or still-queued work for its owner. Queued cancellation is atomic with the terminal receipt and request event; after claim, the same operation refuses cancellation because a later handoff may be uncertain.

The first `claim_queued_power` operation is trusted in-process worker authority only. It is absent from the local socket request set and returns a non-send claim token after durable checks. A local UI or ordinary client cannot acquire that token through a request facade.

`reject_abandoned_claim` is likewise trusted in-process only. It refuses a live monitored claimant and durably rejects a stranded pre-handoff claim. The owner credential cannot invoke it through the local API.

`fence_rule_generation` is a trusted in-process maintenance operation, absent from the local socket. It requires an exact current Store revision and authority epoch and returns the new generation, last journal revision and affected request count. It cannot install a caller-supplied rule or bypass proof admission.

A mutation envelope includes API version, operation ID, authority epoch, expected resource revision, exact targets, typed input and deadline. Identity/credentials come from the authenticated channel, not a caller-supplied role field. Authentication, capability validation, policy and guards precede durable admission. Return a typed rejection or receipt, not an unqualified boolean success.

The initial internal store boundary issues a random 32-byte credential during trusted local principal provisioning and persists only its SHA-256 digest, closed permissions and target grants. Enrollment persists a validated bounded Thing declaration. Request staging authenticates the credential and derives the Thing, permissions, revision and authority epoch inside one writer transaction. Revoked principals cannot submit or read receipts; revoked Things cannot stage new work. Revocation atomically rejects affected held and unsent execution work; a recorded handoff becomes unknown because a packet cannot be recalled. It is not a physical handoff fence. A trusted compare-and-swap declaration reduction also invalidates current reports and held work in one transaction; it cannot add grantable capabilities under an existing target grant. Trusted target-grant revocation removes one principal/Thing grant and only its matching held or execution work; the principal's other grants remain active. Trusted credential rotation returns a new random credential once, revokes the old one and invalidates the principal's held or execution work. Adding one later target is supported only as a trusted atomic grant-and-rotate transaction: an already distributed credential never gains wider scope, and all of that principal's old pending work is invalidated. Duplicate grant attempts leave the credential and revision unchanged. These in-process provisioning operations must not be published as unauthenticated API routes. A narrow opt-in local IPC facade now exists; physical command admission does not.

A principal with exactly the `read` permission may now be provisioned with zero Thing grants. It can authenticate to redacted health before hardware enrollment but receives an empty catalogue and no target observations or held effect authority. An `enroll:review` principal may also have zero target grants so it can review a candidate before any Thing exists; this permission grants no observation or control target. Control, rule-review and qualification permissions still require explicit active targets. The trusted `bin/bootstrap_health.exs` development command issues this fixed diagnostic principal once inside a private foreground host and prints its 43-character credential for manual Keychain import; a repeat returns `principal_exists`. This is a local bootstrap aid, not a socket provisioning route, installed broker or credential recovery mechanism.

The trusted `bin/bootstrap_controller.exs` development command provisions a
named read/control principal against one already enrolled Thing, or adds one
later target through the atomic grant-and-rotate operation. It prints the new
43-character credential once for manual Keychain replacement and stops its
temporary Home application. It neither accepts secret bytes on the command
line nor exposes provisioning through the local request protocol. A control
principal still cannot be provisioned with zero targets.

**H15-06.** The semantic service is implemented as a transport-independent
application authority API. It owns use-case sequencing across authentication,
pure decisions, capture owners and durable transactions. The Unix-socket
server owns peer verification, framing, deadlines and response encoding only.
It does not call the Store, device capture sessions or rule checkers directly.

Direct in-process callers and every external facade use the same authority
operations and receive the same typed results. Transport-specific timeout
handling may convert an unresolved mutating call to `outcome_unknown`, but it
cannot change the committed result. Application operations remain bounded and
must not accept raw SQL, database handles, sockets or driver modules from an
untrusted request.

The local adapter exposes an internal full-frame contract seam that performs
the same strict JSON decoding, closed operation routing and response encoding
without opening a listener. It is not an endpoint and performs no peer check.
Restricted build environments use this seam for deterministic adapter parity;
platform integration still tests Unix-socket ownership, modes and peer
credentials on a host that permits local sockets.

An in-process `Authority.rule_facts` read now obtains 1–32 distinct explicit readable facts from the Store-owned receipt clock and exact journal binding. It requires current `rule:review` plus `read` or `control:ordinary`, and every target grant. It returns `home-reported-facts-v1` / `reported_fact_preview_only`, the Store revision/authority epoch, sampled receipt clock, declaration/report revisions and typed known/unknown facts. The caller supplies no time, source epoch, invariant decision or lease. It changes no revision, generation, receipt or execution row, and is not a socket/CLI route, guard token or admitted runtime. A consumer must obtain current inputs again at any later authority transaction rather than reuse this preview as dispatch evidence.

**H15-02.** Initial admission ceilings are 64 KiB per command, 1 MiB per paginated snapshot page, 100 items per page, 32 pending requests per session and a five-second ordinary request deadline. These are conservative design defaults, not measured device limits. Device, pairing and proof operations use explicit separate deadlines. Input is bounded before allocation; reject duplicate JSON members, excessive nesting and unknown operation fields. Future changes are versioned and tested at each boundary.

The current Store has no long-lived authenticated session; it enforces 32 held requests per principal and 1,024 globally, including calls made in-process. It creates a rejected receipt at the held-work ceiling rather than silently dropping the request. The socket bounds frame reading and ordinary dispatch decisions to one five-second deadline, with a bounded response-send period. A timed-out submit/cancel returns `outcome_unknown`, because its queued Store call can still commit; only status under the original ID resolves it. Draft review has a separate ten-second check deadline. Installed IPC identity and measured end-to-end response timing remain open.

The Store separately caps total retained request IDs at 65,536 by default. Once full, a new operation ID returns `receipt_capacity` without recording a receipt, while existing exact retries and terminal transitions remain available. Authorized health exposes the retained count and ceiling. The caller must treat a capacity error as zero admission, not assume a durable rejection receipt exists. A trusted startup may lower this ceiling; safe pruning and durable disk-reserve policy remain open.

Schema version 5 can represent execution and uncertain-outcome dispositions on the existing scoped `status` and `request_events` reads. Startup converts a recorded but unsettled handoff to `outcome_unknown` before accepting clients; it never treats reconnect or an ACK as physical success. `cancel` is valid for held or still-queued work, never a claimed or handed-off operation. No local API route can promote, claim or consume the execution ledger. The internal supervised worker may do so only after explicit host enablement and qualification; `dispatch_enabled` is false by default and becomes true only while that configured worker is live.

The initial socket wire format is a four-byte unsigned big-endian body length followed by one JSON object. One connection carries one request and one response, then closes. The outer request must have exactly one of these key sets: `{api_version, operation, credential}` for `health`, `support_preview` and `lifx_discover`; `{api_version, operation, credential, thing_id}` for `lifx_refresh`; `{api_version, operation, credential, session_ref, candidate_ref}` for `lifx_interview`; `{api_version, operation, credential, session_ref, candidate_ref, profile_ref, thing_id, review_ref}` for `lifx_enroll` and `lifx_rereview`; `{api_version, operation, credential, mutation}` for `submit`; `{api_version, operation, credential, rules}` for `review_rules`; `{api_version, operation, credential, review_ref}` for read-only `enrollment_status`; `{api_version, operation, credential, target_ids}` for `overrides`; `{api_version, operation, credential, authority_epoch, operation_id, target_id, basis_revision, duration_ms}` for `override_issue`; `{api_version, operation, credential, authority_epoch, operation_id}` for `status`, `cancel`, `override_status` and `override_revoke`; `{api_version, operation, credential, watermark, after, page_size}` for `snapshot` and `catalogue`; `{api_version, operation, credential, after_revision, page_size}` for `events` and `request_events`; or `{api_version, operation, credential, thing_id, capability_key, watermark, after_revision, page_size}` for `history`. `api_version` is integer `1`. The credential is an unpadded URL-safe base64 encoding of 32 random bytes. `mutation` is the closed WOH.01 envelope. `rules` contains 1 to 64 closed WOH.04 draft rules. Responses are similarly framed and contain `api_version`, `outcome` (`ok`, `error`, or `not_found`) and a route-specific `health`, `support`, `receipt`, `snapshot`, `catalogue`, `events`, `request_events`, `history`, `review`, `enrollment_review`, `enrollment_commit`, `lifx_refresh`, `capture`, `interview`, `overrides`, `override_receipt` or `reason`. A receipt disposition of `held` means durable staging only. `cancel` atomically withdraws held or still-queued work owned by the authenticated principal and returns the terminal receipt. No raw driver, profile-qualification or credential-provisioning route is available. A caller should query status using the original `(authority_epoch, operation_id)` after a lost request mutation and query `enrollment_status` using the original review reference after a lost enrollment response; after a lost refresh response it queries the ordinary snapshot because the only possible durable effect is an idempotent observation report. It must not infer physical effect from socket delivery.

The read-only `overrides` route accepts at most 32 distinct granted target IDs and derives its clock inside the Store. It returns only currently active leases with their target, issuer, authority and resource revision plus remaining milliseconds computed from the same Store read. The original operation ID is returned only when the caller is that lease's issuer; other granted readers receive null, and older in-process leases without an operation receipt also have no ID. A read or ordinary-control principal can see only granted targets. A client-supplied timestamp or extra field is rejected. The `overrides` read route cannot issue, extend, revoke or activate an override. The implemented closed mutation routes are `override_issue` with credential, authority epoch, operation ID, target ID, basis revision and duration milliseconds; `override_revoke` and `override_status` with credential, authority epoch and operation ID. Issue and revoke return a scoped receipt with original issue revision, active state, remaining time and optional revoke revision. Issue recalculates active state after its transaction before replying. These calls use the Store clock; no client timestamp is accepted. A timed-out issue or revoke reports `outcome_unknown`, and status under the same tuple resolves its durable result. The Store authenticates the current control grant before exposing conflict state, so a read-only caller cannot infer another operator's lease by attempting an issue. No route creates an automation or driver command.

The private Unix socket now requires a same-effective-UID kernel peer before it reads the frame. A client from another UID, or a platform whose peer credential layout cannot be checked, is closed. This narrows the local IPC audience but does not identify a signed app or replace the scoped bearer credential. Installed lifecycle and session tests are still required.

The production release sets `RELEASE_DISTRIBUTION=none`, so it does not register an Erlang node or listen for distributed Erlang peers. The private Unix socket remains its intended local request path. A release smoke asserts `Node.alive?()` is false before exercising the bundled verifier and host startup; installed network and lifecycle checks remain open.

The internal Elixir client checks the private parent/socket modes and matching owner, then verifies the connected server peer's effective UID before sending the credential. It also checks request size and depth, caps response bytes at 1 MiB, rejects duplicate response members and unsupported response versions, and closes each connection. A missing or wrongly permissioned endpoint fails before send; a response lost after send remains uncertain for mutations. Its deadline covers connection and frame I/O; the server's own operation deadline remains a separate open gate.

The packaged `wotex_home_cli` now uses that client for `health`, redacted `support-preview`, operation `receipt`, `enrollment` review status and one-target `overrides` reads, plus `submit`, `cancel`, `override-issue`, `override-status` and `override-revoke`. `support-write` fetches a fresh authenticated preview, validates its exact closed schema and writes a new 0600 file at the operator's absolute path; the socket never accepts a host-side file destination. It also exposes bounded `catalogue`, `snapshot`, `events`, `request-events` and single-capability `history` pages. LIFX commands cover discovery, interview, one-use packaged enrollment and fresh re-review; every enrollment argument is an opaque reference, and an uncertain response directs the operator to `enrollment REVIEW_REF`. A first catalogue/snapshot/history call supplies the null watermark contract; continuation calls explicitly carry the returned watermark and cursor. The CLI emits one page per call and passes no implicit cursor across invocations. `review-rules` reads one private bounded JSON object with exactly a `rules` list, rejects duplicate members and closed-rule validation failures before calling the authenticated draft review route. Its `pending_positive_basis` result does not admit or activate a rule. The CLI requires an explicit absolute socket path and a regular 0600 file containing one canonical 43-character credential; credentials are not command arguments or echoed. `submit` reads a closed, bounded mutation envelope from an absolute regular 0600 JSON file and rejects duplicate members. Open file descriptors are checked against their pre-open inode and private mode. The CLI prints the closed JSON response and distinguishes success, not-found, usage, uncertain mutation and local failure by exit code. Staging returns `held` and cannot claim a physical effect. The CLI has no provisioning, profile-qualification or driver route. Each operation still requires the Store permission and target grant where that operation has a target.

`review_rules` requires the separate `rule:review` permission and at least one granted active Thing. It screens only those declarations, outside the Store writer, then reauthenticates and requires the same global revision before responding. A concurrent write returns `resnapshot_required`; revocation returns `unauthorized`. The response contains decision, reason, profile, rule and registry digests and watermark. It does not include checker witness data, save the review, admit a rule or send a device command. A principal may hold both `control:ordinary` and `rule:review`; the policy checks the permission for each operation independently. The current 32-target principal limit bounds the review registry. At most two reviews run simultaneously; a third receives `review_capacity` without waiting. Device and installed-host timing still require qualification under their separate deadlines.

For the exact one-rule explicit Boolean Light subset, `review_rules` may also return a nullable `proposal_basis` object with target ID, basis profile, `proposal_generation_only` scope, obligation names and rule/declaration/runtime digests. The current `explicit-boolean-light-v3` shape also includes `compiler_profile`, `source_digest` and `ir_digest`, binding the complete source-bound IR used by the evaluator. The route returns no AST, raw IR or native witness; these scalar commitments are not command tokens. It is produced before the same final credential/revision check. The top-level decision remains pending and no activation endpoint accepts this object. Other candidates return `proposal_basis: null`.

`lifx_discover` first authenticates a current `enroll:review` principal, then asks the opt-in capture owner to send one bounded GetService query with an owner-generated correlation key. Its response contains one random session reference and at most 128 untrusted candidate summaries. `lifx_interview` requires that same principal and an exact candidate reference from the current session. The capture owner refuses a second operator's discovery while that session is live, refuses another operator's interview even with the reference, and checks a three-second admission deadline before starting queued network work. It exposes reported identity plus only the matching compiled profile summaries: profile reference, fingerprint tuple, capability keys, qualification reference and explicit pending status. A missing capture owner returns `capture_unavailable`.

`lifx_enroll` and `lifx_rereview` are the only external-route consumers of operator-bound socket evidence. An unbound lab checkout or another operator ID gets `capture_missing` without consuming it. Unsupported profile and malformed selection references are rejected before checkout. After checkout, exact profile mismatch or Store rejection consumes the evidence fail-closed; the client must capture again rather than edit or replay it. The initial compiled profile is power-only and pending physical qualification. The headless CLI exposes discovery, interview, enrollment, re-review and status with the same private credential-file rules; none of these operations grants target permissions or device-send authority.

`lifx_refresh` accepts only one Home Thing ID in addition to the credential. It requires a current `read` or `control:ordinary` permission and current target grant before network work. Authority obtains the active enrolled stable ID, exact declaration and resource revision from the Store, asks the capture owner for a fresh discovery/read, receives only protocol-validated observations, then repeats the credential, target, binding, declaration and revision checks inside the Store transaction. The device session receives no credential or persistence capability. The route never accepts or returns a device endpoint, LIFX target, candidate or profile body. Refresh is unavailable while an enrollment capture remains live. A timeout can race a valid report commit, so the response is `outcome_unknown` and the recovery read is a scoped snapshot rather than a mutation receipt. The headless CLI exposes this as `lifx-refresh THING_ID`; it creates no continuous polling authority.

## Snapshots and streams

The single writer now delegates its bounded principal-scoped paging projections
to `Store.StateReadModel`. Snapshot/catalogue watermarks, hidden-event cursor
advancement, history access and the closed request-state vocabulary are shared
by direct and framed Authority calls; a read projection cannot create a writer
or revision.

**H15-03.** A snapshot has an authority epoch and store watermark. Events carry monotonic service cursors, not device timestamps as cursors. Reconnection resumes a retained range or receives `resnapshot_required`; it never silently skips a gap. A revoked session cannot continue reading a formerly authorized stream. Each subscriber has bounded credit/queue state; slow consumers disconnect or receive an explicit gap. Command outcomes remain queryable independently of stream loss.

The implemented `snapshot` subset lists current observations only for an active principal's granted, active Things. It includes typed value, quality, trust, profile/evidence reference, source time, receive time, boot epoch and row revision. A first page supplies `watermark: null`, `after: null`, and `page_size` from 1 to 100. The response returns the authority epoch, global store revision as `watermark`, ordered `items`, and `next_after` (a `{thing_id, capability_key}` pair or null). Later pages reuse that watermark and pass `next_after`. Any intervening store write yields `resnapshot_required`; the caller starts again. Revocation is checked per page. This is a bounded consistency protocol, not retained-history paging or an event stream. Event cursor/credit/resume behavior remains open.

The implemented `catalogue` subset uses the same global watermark and revocation rule to page active Thing declarations scoped to the principal's target grants. Its `after` and `next_after` fields are Thing IDs (or null), and its page size is 1 to 10 because each validated declaration may occupy up to 64 KiB. It returns the canonical capability declaration and resource revision, not a driver route or credential. Clients should obtain catalogue and observations at the same watermark; if either page reports `resnapshot_required`, restart both reads.

The implemented `history` subset pages the append-only observation journal for one granted capability on an active Thing. The first page uses `watermark: null` and `after_revision: 0`; subsequent pages reuse its watermark and the returned `next_after` revision. A write between pages requires a restart. Each item retains typed value, provenance and source/receive times. Current credentials, grants and enrollment are checked on every page. This is historical report evidence, not an event stream or proof of physical effect; retention and explicit old-cursor gaps remain open.

The implemented `events` subset polls observation journal entries across the caller's granted active Things after a global revision cursor. It returns at most 100 ordered items, a current `watermark`, `has_more` and `next_after`. When `has_more` is true, continue from the last returned revision; otherwise `next_after` advances to the watermark even if only hidden writes occurred. Each page rechecks the credential, permissions, grants and active enrollment. A caller can first take a complete snapshot and then poll from its watermark. This is a bounded read-only observation feed, not a push subscription, a command outcome stream, retention-gap handling or credit-based backpressure.

The implemented `request_events` subset pages the authenticated principal's request journal after a global revision cursor, including all closed ledger dispositions. Each item contains authority epoch, operation ID, disposition, reason and revision; malformed states and oversized reasons fail closed. Another principal's writes are skipped while an exhausted page advances `next_after` to the current watermark. The credential is rechecked on every page, including after revocation. This supports reconnecting to durable receipt transitions, including a recovered unknown handoff, but it is not physical-state proof, a retained-gap protocol or a substitute for `status` on a known operation ID.

## Local and remote transports

The macOS baseline uses a private Unix domain socket as specified in WOH.08. An optional LAN HTTPS facade uses explicit local enrollment and credentials. A trusted local CA or pinned peer identity may be used; certificate verification is not disabled to simplify setup. Plain device protocols behind the controller do not justify plaintext administration.

**H15-04.** Matter, Refpath and future external tools submit structured requests under restricted principals. They cannot invoke raw code, choose model include paths, extract keys or call driver methods. Structured requests bypass only natural-language classification, never policy. HTTP/IPC or Matter acknowledgement cannot falsely announce completed physical effect.

## Transfer and restart

A socket-free test now initializes the actual Host child specifications and
retains the Store/gate/power rest-for-one restart tree while omitting OS
adapters. Killing the Store stops its dependent power workers and replaces the
pool before the new host is healthy. OS endpoint and installed lifecycle tests
remain separate; this fixture cannot establish cross-host isolation.

The trusted in-process Authority can explicitly reconcile an unknown direct
LIFX power receipt against exact newer retained evidence. This operation has no
socket/CLI route and no send capability. It repeats owner/grant/epoch/profile
checks in Store and refuses a live worker; a status reply remains the external
receipt recovery surface.

**H15-05.** At most one controller owns a deployment's mutating driver connections. Local process locks prevent a duplicate instance on the same host. A database epoch alone cannot fence a second computer talking to an unauthenticated bulb. Cross-host transfer must quiesce and revoke/isolate the old writer, stop its device channels, transfer current state and credentials through an explicit workflow, then enable the new writer. If isolation cannot be established, transfer remains blocked. Network-level fencing, where used, must be tested rather than assumed.

The initial Store opens a separate SQLite lock database beside the authority database in exclusive WAL mode and keeps its connection for the Store lifetime. A second Store on that path cannot start until the first releases the lock. The separate file permits diagnostic reads of the authority database while the lock is held. This is a same-host process gate only; it does not establish cross-host fencing, prevent a privileged process from opening the database directly, or authorize device connections.

The authority epoch identifies this fenced controller ownership and changes only when ownership is explicitly transferred or recovered. Rule activation advances a separate active-rule generation under WOH.04. Operation IDs are scoped to a principal and authority epoch; a stale epoch is rejected even when the rule generation has not changed.

There is no automatic promotion during a network partition. A second Mac or Nerves gateway may inspect through authorized read APIs; it does not reconcile actuators independently. Legacy devices may also be changed by an external app or physical switch; Home reports and arbitrates those changes instead of asserting exclusive ownership it cannot enforce.

`Authority.set_invariant` and `invariant_status` are authenticated in-process policy operations, absent from the public socket. The separate `policy:manage` permission never grants enrollment, review, qualification or control. Installation compares the full Store revision and previous target policy revision and retains an immutable principal/epoch/operation receipt. Replacement invalidates pending work in the same transaction; supplied clocks or truth decisions cannot replace Store-owned fact consumption.

## Implemented restricted rule lifecycle facade

`admit_rule` accepts exactly `api_version`, `operation`, `credential`, `authority_epoch`, `operation_id`, `expected_revision` and `rules`. It rebuilds the closed single-effect admission argument internally, uses the bounded review gate/ten-second deadline and returns an immutable scalar receipt. `activate_rule` replaces `rules` with `admission_revision`; zero suspends. Both require current rule-management, review and ordinary-control permission and relevant target grants. `rule_operation_status` accepts credential/epoch/operation identity, is principal-private and resolves unknown admission/activation replies without re-execution. No supplied proposal receipt or digest is an activation token.

`invoke_rule` accepts exactly `api_version`, `operation`, `credential`, `authority_epoch`, `operation_id`, `rule_generation` and `rule_id`. Current ordinary-control authority plus the target grant creates a normal held request with an immutable rule origin; its uncertainty is resolved through existing request `status`. `rule_status` accepts the version, operation and credential and returns the active admission, generation, epoch and current active/inactive/suspended state. Management status exposes no private source or proof bytes. Closed fields and real Unix-socket/CLI integration cases cover all routes.

CLI parity is `admit-rule EPOCH OP EXPECTED RULES_FILE`, `activate-rule EPOCH OP EXPECTED ADMISSION_REVISION`, `invoke-rule EPOCH OP GENERATION RULE_ID`, `rule-status` and `rule-operation-status EPOCH OP`. Files use the existing bounded private-file rules. These routes cannot qualify hardware or directly consume the device execution ledger. The native shell reads current rule status, suspends through `activate_rule` with admission revision zero and resolves original admission/activation operations. Native source editing, admission and explicit invocation remain separate work.

## Host maintenance facade

`begin_maintenance` accepts exactly version, operation, credential, authority epoch, operation ID and expected Store revision. `end_maintenance` adds the original `begin_revision`. Both require `host:maintain`; ordinary control alone does not grant this permission. `maintenance_status` takes only version/operation/credential and returns Store revision, epoch, generation, active begin revision and normal/maintenance state. `maintenance_operation_status` uses the original epoch/operation ID and returns only that principal's immutable receipt, including historical affected/unknown counts. The ordinary mutation deadline and uncertain-commit recovery apply. The socket cannot supply an update path, artifact, backup key, installer command or device-maintenance request.

CLI commands are `maintenance-begin EPOCH OP EXPECTED`, `maintenance-end EPOCH OP EXPECTED BEGIN_REVISION`, `maintenance-status` and `maintenance-operation-status EPOCH OP`. After a lost reply, query the original operation before proceeding. Independent authority cases and a real private Unix socket cover the four closed routes.
