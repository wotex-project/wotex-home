# Local scheduler v1

Version: 0.1.0. Owner: WOH.04, H04-07/H04-T8–H04-T10. Status: accepted target; autonomous scheduler and temporal admission planned.

## One admitted automation runtime

The controller, not Swift, launchd, cron, a browser or a cloud service, owns
autonomous scheduling. Closing the UI or disconnecting all clients does not
stop a running owner's admitted work. A sleeping/offline owner cannot execute.
This profile is a successor to the rule grammar/admission profile, not a
reinterpretation of `home-explicit-light-admission-v1`. The implemented
explicit-request profile cannot acquire timers by attaching schedule metadata.
Unsupported temporal or composed proof remains inactive.

First delivery supports one ordinary-risk absolute effect per occurrence:
calendar once, daily or selected weekdays at one local time; a UTC-anchored
fixed interval; and a boot-local countdown. Each binds an admitted rule/source
revision and its exact target/declaration/profile/proof basis. It uses the
existing three-valued predicates, whole-Thing arbiter, current constraints,
operator overrides, spacing, causal budget and receipt path. Toggle, relative
increment, arbitrary cron/RRULE, scripts, solar calculations, remote calendars,
multi-step orchestration and safety-device maintenance are outside this first
profile. Broader forms require their own bounded temporal/proof semantics.

The schedule's original author must currently possess the required rule-review,
rule-management, ordinary-control and exact target/input grants. The runner
holds no distributed operator bearer. Its internal occurrence operation derives
the stored author and active basis, then the Store rechecks them. Losing an
author's authority suspends dependent work; a scheduler's privileged process
identity cannot replace the author's missing grant. A new author/revision needs
explicit admission, never automatic ownership reassignment.

## Time and recurrence

Calendar schedules bind an IANA time-zone name, exact installed tzdata digest,
local date/time or weekdays, start bound, optional end bound and fixed policy:
nonexistent recurring local times are skipped; repeated local times use the
first occurrence once. A one-shot ambiguous/nonexistent local input requires
the operator to choose an explicit valid UTC instant during review. The UI
shows resolved future instants and DST consequences. The controller's zone
does not follow a traveling laptop or a changed OS setting. Updating tzdata
creates a reviewed successor calculation basis, fences old work and never
rewrites historical occurrences. This bounded profile is not an iCalendar
implementation; [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545) provides the
recurrence/DST comparison used to choose these policies.

Fixed intervals bind an explicit UTC anchor and an integer period from one
minute to 31 days. Occurrence `n` is derived from that anchor, not from the last
successful send. It requires trustworthy wall time across restart and skips
missed intervals; no drift or burst is generated by completion latency. A
countdown binds the current Store boot epoch and a monotonic duration from one
second to 24 hours. Restart, controller transfer or an unqualified sleep-clock
discontinuity expires that countdown with a visible missed outcome. Persisted
daily/interval schedules retain definitions across restart. An ordinary restart
of the same owner can resume an already admitted schedule only after the current
basis is revalidated as defined below; restoring copied data grants no admission.

Clock input is host-owned, with source identity, boot/clock generation,
confidence and an explicit UTC uncertainty interval. It must be established by
a qualified local clock/RTC or trusted local setup; a device report, client
timestamp or successful DNS lookup is not trusted time. Public NTP is optional.
Clock behavior and oscillator/RTC bounds must be qualified for the actual host.
Calendar and fixed-interval effects are blocked when uncertainty exceeds the
schedule's admitted tolerance. Manual effects remain subject to their existing
guards and are not globally disabled merely because WAN time is unavailable.
Recovery trust and TLS certificate validity keep their separately owned checks.

UTC-to-monotonic conversion is boot/clock-generation scoped. Before admitting a
due effect, the whole UTC confidence interval must fall within its admitted
occurrence window. First delivery allows a one-to-60-second late window and
zero early tolerance, expressed as the half-open interval
`[due, due + late_window)`. Time correction, wake or clock-generation change
invalidates precomputed deadlines and unsent temporal work; fresh calculation
and current admission are required. Moving time backward cannot repeat an
already considered occurrence. Moving it forward skips elapsed windows rather
than replaying them. Leap seconds are outside the source grammar; seconds are
0–59 and the qualified host's time policy is recorded.

## Durable occurrence and effect boundaries

Each occurrence has a deterministic identity bound to home authority epoch,
schedule/source revision, active generation and canonical UTC instant/interval
index, or boot epoch/countdown identity. It is not minted afresh on each poll.
Its receipt distinguishes scheduled, skipped/missed, blocked, admitted and
the existing effect dispositions. Neither a due timer nor `protocol_accepted`
means that a light changed physically.

The scheduler computes bounded candidates outside the writer. One Store
transaction validates the current schedule, generation, author, time basis,
facts, target, policy, override and qualification assumptions; reserves the
occurrence identity and causal root; and creates the normal held intent or
records a terminal blocked/missed outcome. Concurrent ticks, crash/restart and
lost responses cannot create a second intent for the same occurrence. Claim
and final handoff repeat the current temporal and ordinary guards. A reserved
effect is never refunded by cancellation, restart, activation change or unknown
handoff. A late/expired unsent occurrence cannot dispatch simply because it was
admitted on time. Existing durable receipts remain the authority for status.

Default missed policy is `skip`, including sleep, downtime, maintenance,
uncertain clock, revoked assumptions and a saturated queue. First delivery has
no catch-up/retry of a blocked occurrence and no replay of effects after a
handoff. The UI offers an explicit fresh manual request when appropriate.
Future bounded catch-up needs a separately proved absolute-effect policy;
idempotent desired values alone do not prove safe repetition or physical cause.

Activation/replacement/suspension uses the existing generation/CAS transaction.
Changing the time, zone, effect, predicate, author or artifact basis creates a
new revision. No occurrence from before activation becomes eligible. Transfer,
backup restore and maintenance retain occurrence history but do not silently
reactivate schedules. These transitions require current admission under the
actual owner. Ordinary same-owner, same-cohort restart is different: it may
automatically resume the retained generation after Store integrity/ownership,
artifact/proof assumptions, original author/grants and clock basis are
revalidated. It requires no UI or available optional verifier when the retained
proof remains valid. Fresh inputs still gate individual effects. A missing,
changed or unproved basis suspends that schedule with a concrete reason; it
cannot be reconstructed from a label or activated merely because the process
booted. Countdowns expire and missed calendar/interval occurrences stay skipped.
The admission profile must prove this restart transition before delivery.

The initial active set is bounded to 64 rules/schedules in total, with at most
16 candidate occurrences per writer batch and one in-flight batch. Capacity
must be reserved before activation; ordinary schedules cannot consume a separately
reserved safety-response lane. No unbounded timer per historical recurrence,
polling-triggered retry loop or arbitrary future expansion is allowed. Retain a
monotonic considered-through watermark and original receipts so bounded history
compaction cannot make old occurrences eligible again. Exact encodings,
migration, retention ceilings, active-set arbitration and the independent
temporal correspondence oracle are implementation-entry obligations.

Before batching, arbitrate all eligible proposals in the bounded active set
under one current generation/time/declaration basis. Equal-authority incompatible
effects yield a conflict; a 16-item batch cutoff or timer arrival order cannot
choose a winner. Commit revalidates the complete arbitration basis. More than
one active rule/schedule remains unsupported until the composed admission
profile proves those semantics. Long downtime is accounted for with a bounded
missed-range summary and considered-through watermark, rather than allocating
an intent/receipt for every historical tick. Compaction preserves the exact
no-repeat boundary and all existing uncertain-effect receipts.

## Sensor-triggered successor

Reported-edge automation is a separate admitted successor, though it uses the
same runner and receipt machinery. Inputs must be current qualified reports,
not acknowledgements, MQTT retained replay or an initial restored snapshot.
First report/reconnect establishes a baseline and creates no synthetic rising
edge. Bound source epoch/sequence, input revision, debounce/cooldown, three-valued
unknown handling and causal lineage in its proof. Profile replacement, stale
input, source-epoch change and author/grant loss invalidate that baseline.
Derived occupancy/estimates retain their provenance and are not physical motion.
No rule receives a raw transport subscription with mutation authority.

additional installed/hardware evidence, not supplied by pure time fixtures.
